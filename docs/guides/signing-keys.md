# Signing keys and rotation

Every access token and OIDC ID token is an RS256 JWT whose `kid` header names
the key that signed it. `GET /.well-known/jwks.json` publishes the public half
of every key that can still verify a token.

## Deployment key and environment keys

- The **deployment key** (`JWT_PRIVATE_KEY_PATH`) signs for every environment
  that has no active key of its own. Its `kid` is derived from the public key,
  so it does not change across restarts. It verifies tokens of any environment.
- An **environment key** is generated by IAMKit (RSA-2048), stored with its
  private half sealed by `IAMKIT_ENCRYPTION_KEY` and signs only its own
  environment's tokens. A token whose `kid` belongs to another environment is
  refused. Creating one without `IAMKIT_ENCRYPTION_KEY` answers 422
  `ENCRYPTION_KEY_REQUIRED`.

Environments without keys keep working exactly as before: nothing changes until
you activate a key.

## Key states

| State | Published in JWKS | Signs | Next |
| --- | --- | --- | --- |
| `next` | yes | no | `active`, `retired` |
| `active` (one per environment) | yes | yes | `retiring` (when another key is activated) |
| `retiring` | yes | no | `active` again, `retired` |
| `retired` | no | no | — |

## Rotate

1. **Create** a `next` key: console **Signing keys → Create key**,
   `iam signing-keys create`, `POST …/signing-keys` or the SDK's
   `CreateSigningKey`. It is published at once.
2. **Wait** for relying parties to refresh their cached JWKS. The Go SDK's
   `authclient.KeySet` refreshes every 10 minutes and on an unknown `kid`;
   waiting at least that long covers typical caches.
3. **Activate** it (`iam signing-keys activate KID`). New tokens are signed with
   it; the previously active key becomes `retiring` with `retire_after` set
   20 minutes ahead (longer than any access token's 15-minute lifetime), and
   keeps verifying.
4. **Retire** the old key once `retire_after` has passed
   (`iam signing-keys retire KID`). It leaves the JWKS; tokens it signed stop
   validating. Retiring before `retire_after` answers 409 `KEY_IN_USE` unless
   you pass `force` (`--force`, console **Retire now**, which asks you to type the
   key ID).

The active key cannot be retired directly: activate its replacement first. To
roll back, activate the `retiring` key again. A retired key never returns.

Every change is audited (`signing_key.create`, `signing_key.activate`,
`signing_key.retire`).

## Compromised key

Create and activate a replacement, then retire the compromised key with
`force`. Tokens it signed stop validating immediately; affected users sign in
again. Refresh tokens are opaque and keep working, so sessions renew with the
new key. A compromised **deployment** key still needs the file-level procedure
in [secrets and keys](../operations/secrets-and-keys.md#signing-key-change).

## Replicas and caching

Replicas share the key table. Each caches the published keys for 30 seconds and
reloads at once (at most once per second) on an unknown `kid`, so a key
activated on one replica is honoured everywhere. If an active key cannot be
opened (for example `IAMKIT_ENCRYPTION_KEY` changed without keeping the old key
in `IAMKIT_ENCRYPTION_KEYS_OLD`), that environment refuses to sign rather than
silently falling back to the deployment key.
